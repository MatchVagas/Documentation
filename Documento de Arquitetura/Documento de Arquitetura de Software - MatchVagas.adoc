[[introducao]]
== INTRODUÇÃO
[.text-justify]
Este documento descreve a arquitetura do MatchVagas, sistema de vagas de trabalho e estágio que conecta candidatos, empresas e administradores. A revisão v3.1 registra apenas tecnologias sustentadas pelos artefatos atuais e marca explicitamente decisões pendentes e componentes de roadmap.

[[finalidade]]
=== Finalidade
[.text-justify]
O Sistema MatchVagas é uma plataforma web que visa centralizar oportunidades de trabalho e estágio, facilitando o contato entre candidatos e empresas. O projeto foi idealizado para oferecer um ambiente intuitivo e seguro onde candidatos possam construir seus perfis, buscar vagas compatíveis e acompanhar candidaturas, enquanto empresas podem publicar e gerenciar suas vagas de forma eficiente. 

Este documento oferece uma visão arquitetural geral do sistema, usando diversas visões arquiteturais para representar diferentes aspectos do mesmo. O objetivo deste documento é capturar e comunicar as decisões arquiteturais significativas que foram 
tomadas no decorrer do processo de desenvolvimento.

[[escopo]]
=== Escopo
[.text-justify]
Este documento descreve a arquitetura de software do Sistema MatchVagas, abrangendo a estrutura de alto nível, os componentes principais, as interações entre eles e as decisões arquiteturais que atendem aos requisitos funcionais e não funcionais especificados. 
Este documento auxilia os envolvidos no projeto a captar aspectos arquiteturais do sistema que são necessários para o desenvolvimento de uma solução que atenda às necessidades dos usuários finais. Além de auxiliar no entendimento do sistema por novos membros da equipe.

O Sistema MatchVagas adotará uma arquitetura cliente-servidor baseada na web, seguindo o estilo arquitetural de camadas (n-tier) para separar responsabilidades e facilitar a manutenção e evolução do sistema. A arquitetura é composta por três camadas principais:

. *Camada de Apresentação (Frontend)*

* Interface web responsiva, acessível via navegadores modernos (desktop e mobile).

* Comunica-se com o backend por meio de requisições HTTP/HTTPS utilizando APIs REST.

* Implementa as diretrizes de acessibilidade WCAG 2.2 nível AA.

. *Camada de Negócio (Backend)*

* Expõe uma API RESTful que encapsula a lógica de negócio e as regras do sistema.

* Responsável por autenticação, autorização, validação de dados, orquestração dos processos (cadastro, busca, candidatura, etc.).

* Implementa as medidas de segurança (hash de senhas, HTTPS, conformidade com LGPD).

* A implementação declarada utiliza Java/Spring Boot; alternativas de linguagem não fazem parte desta baseline.

. *Camada de Dados (Banco de Dados)*

* Banco de dados relacional com integridade referencial e transações ACID. A tecnologia concreta deve ser confirmada e registrada antes da aprovação, pois os artefatos atuais divergem entre MySQL e PostgreSQL.

* Armazena informações de usuários, perfis, vagas, candidaturas e logs administrativos.

* Índices otimizados para consultas de busca e filtragem, visando o tempo de resposta inferior a 3 segundos.

//A comunicação entre as camadas ocorre de forma segura (HTTPS) e stateless, utilizando tokens JWT para gerenciamento de sessão após autenticação. O sistema será hospedado em ambiente cloud com balanceamento de carga para garantir alta disponibilidade (99,5% no horário comercial).

[[requisitos]]
== REQUISITOS E RESTRIÇÕES ARQUITETURAIS

A arquitetura deve atender aos seguintes requisitos e restrições, derivados principalmente dos requisitos não funcionais (RNF) e das necessidades do negócio:

. Linguagem e Plataforma
* Backend: Java/Spring Boot, conforme implementação declarada no ERS v5.1.
* Frontend: tecnologia a confirmar; registrar repositório, framework e versão suportada.
* Banco de dados: relacional; selecionar e documentar uma única tecnologia canônica.
. Segurança
* Todas as comunicações devem utilizar HTTPS (RNF003).
* Senhas armazenadas com hash seguro (bcrypt) (RNF003).
* Conformidade com a LGPD: coleta de consentimento, proteção de dados pessoais (RNF004).
* Controle de acesso baseado em papéis (candidato, empresa, administrador).
. Disponibilidade e Desempenho
* Disponibilidade mínima de 99,5% no horário comercial (08h–20h) (RNF001).
* Tempo de resposta para buscas, filtros e candidaturas inferior a 3 segundos (RNF002).
* Estratégias de cache para consultas frequentes (ex.: listagem de vagas).
. Integridade e Confiabilidade
* Transações ACID para operações críticas (cadastro, candidatura) (RNF007).
* Validação de dados em frontend e backend; impedir candidaturas duplicadas (RNF010).
. Manutenibilidade e Evolução
* Código fonte versionado com Git, seguindo boas práticas (Clean Code, padrões de projeto) (RNF008).
* Documentação da API (ex.: OpenAPI/Swagger).
. Acessibilidade e Usabilidade
* Atender WCAG 2.2 nível AA com critérios ligados a testes (RNF005).
* Design responsivo e intuitivo (RNF009).
. Compatibilidade
* Publicar matriz por release e testar a versão atual e anterior de Chrome, Firefox, Edge e Safari (RNF006).

Essas restrições guiam a escolha de tecnologias, a definição da arquitetura de implantação e as práticas de desenvolvimento.

[[visaocasouso]]
== VISÃO DE CASOS DE USO

A visão de casos de uso representa as funcionalidades principais do sistema sob a perspectiva dos atores. O diagrama de casos de uso do MatchVagas (fornecido em anexo) ilustra as interações entre candidatos, empresas/recrutadores e administradores.

[[casosusosig]]
Os principais casos de uso identificados são:

Candidato::

* Gerenciar perfil (dados pessoais, formação, experiências, currículo) – [RF003]

* Buscar e filtrar vagas – [RF007]

* Candidatar-se a vagas – [RF008]

* Acompanhar candidaturas – [RF009]

* Visualizar recomendações de vagas

Empresa/Recrutador::

* Gerenciar perfil da empresa – [RF004]

* Cadastrar vagas – [RF005]

* Manter vagas (editar, desativar, remover) – [RF006]

* Visualizar candidaturas recebidas

* Gerenciar processos seletivos

Administrador::

* Gerenciar usuários (criar, editar, bloquear) – [RF010]

* *Aprovar ou rejeitar cadastros de empresas* – [RF004, RF010]

* Gerenciar vagas (moderar, remover)

* Visualizar relatórios do sistema

* Configurar parâmetros gerais

=== Casos de Uso significantes para a arquitetura

Alguns casos de uso têm impacto direto na arquitetura por envolverem alta complexidade, requisitos de desempenho ou integração com múltiplos componentes:

Busca e Filtragem de Vagas [RF007]::
Necessita de índices eficientes no banco de dados, possibilidade de uso de mecanismos de busca textual (ex.: Elasticsearch) para garantir desempenho e relevância. A arquitetura deve prever uma camada de busca otimizada que possa ser escalada horizontalmente.

Cadastro e Autenticação [RF001, RF002]::
Envolve segurança (hash de senha, proteção contra ataques), gerenciamento de sessões (JWT) e integração com a LGPD. A arquitetura deve separar claramente os serviços de autenticação e autorização.

Candidatura e Acompanhamento [RF008, RF009]::
Operações que exigem consistência transacional (evitar duplicidade) e notificações em tempo real (ou quase) sobre mudanças de status. Pode-se utilizar filas (message brokers) para processamento assíncrono de notificações.

Administração do Sistema [RF010]::
Funcionalidades que demandam interface específica e acesso a dados agregados (relatórios). A arquitetura deve prever a separação dos painéis administrativos dos fluxos comuns, garantindo segurança e isolamento.

Esses casos de uso guiam a definição dos módulos e serviços da aplicação, bem como as decisões sobre escalabilidade e armazenamento.


[[visaologica]]
== VISÃO LÓGICA

A visão lógica descreve as principais entidades de domínio e suas relações, organizadas em camadas. Abaixo estão as principais classes (ou agregados) que sustentam a aplicação:

. Usuário (abstrata)

* Atributos: id, nome, e-mail, senha (hash), tipo (candidato, empresa, admin), data de cadastro, status
* Especializações: Candidato, Empresa, Administrador

. Candidato

* Atributos: CPF, data de nascimento, idade, telefone, endereço, currículo (arquivo ou texto)
* Relacionamentos: um para muitos com Formacao, Experiencia, Candidatura

. Empresa

* Atributos: CNPJ, razão social, nome fantasia, descrição, porte, ramo, site, endereço, contato, *status (PENDENTE | APROVADA | REJEITADA)*
* Relacionamentos: um para muitos com Vaga
* *Fluxo de aprovação*: ao ser criada por um usuário do tipo EMPRESA, a entidade recebe status `PENDENTE`. O administrador pode aprovar (`APROVADA`) ou rejeitar (`REJEITADA`) o cadastro. Apenas empresas com status `APROVADA` aparecem nas listagens públicas. Quando o próprio administrador cria a empresa, o status inicial é `APROVADA`.

. Vaga
* Atributos: título, descrição, requisitos, tipo (trabalho/estágio), localidade, data de expiração, status (ativa/inativa), data de publicação
* Relacionamentos: muitos para um com Empresa; um para muitos com Candidatura

. Candidatura

* Atributos: data da candidatura, status (em andamento, aprovada, rejeitada), histórico de alterações
* Relacionamentos: muitos para um com Candidato e Vaga (garantindo unicidade por par candidato-vaga)
* Formação e Experiência (agregados de Candidato)
* Formação: instituição, curso, nível, ano de conclusão
* Experiência: empresa, cargo, período, descrição

. Administrador (herda de Usuário)
* Pode realizar operações de gestão sobre usuários, vagas, candidaturas e empresas.
* Responsável por aprovar ou rejeitar cadastros de empresas, controlando quais perfis ficam visíveis na plataforma.
