== Introdução

=== Propósito
Este documento tem como objetivo especificar de forma clara, completa e verificável os requisitos do Sistema de Banco de Vagas de Trabalho e Estágio, servindo como referência para clientes, desenvolvedores, testadores e demais partes interessadas.

=== Especificação de Requisitos de Software
O documento de requisitos descreve os requisitos funcionais e não funcionais que o sistema deve atender, apresentando os seguintes tópicos:

* *Descrição geral do sistema*: visão geral do escopo e dos usuários.
* *Requisitos funcionais*: descrevem os fluxos de eventos, prioridades, atores, entradas e saídas de cada funcionalidade implementada.
* *Requisitos não funcionais*: descrevem restrições de qualidade, desempenho, segurança e conformidade legal.

=== Escopo do Sistema
O sistema permitirá o cadastro, divulgação e gerenciamento de vagas de trabalho e estágio, bem como o cadastro de candidatos e empresas, possibilitando candidaturas e acompanhamento do processo seletivo de forma segura e em conformidade com a LGPD.

Principais benefícios:

* Seu primeiro emprego ou estágio começa aqui.
* Centralização das oportunidades de trabalho e estágio.
* Facilitação do processo de candidatura com controle de privacidade.
* Apoio ao recrutamento por parte das empresas.
* Sugestão inteligente de vagas compatíveis com o perfil do candidato.

== Descrição Geral do Sistema

=== Perspectiva do Produto
O sistema é uma aplicação web independente com arquitetura cliente-servidor. O backend expõe uma API RESTful (Spring Boot 3 / Java 21) com autenticação via JWT stateless. O banco de dados é relacional (PostgreSQL/MySQL) com garantias ACID.

=== Funções do Produto
* Cadastro e autenticação de usuário com perfil por tipo (CANDIDATO, EMPRESA, ADMIN).
* Gerenciamento completo de perfis: candidatos (formação, experiência, currículo), empresas (com fluxo de aprovação) e administradores.
* Cadastro, manutenção e busca/filtragem de vagas de trabalho e estágio.
* Candidatura a vagas com controle granular de privacidade (LGPD).
* Acompanhamento de candidaturas pelo candidato e pelo recrutador, com visões separadas.
* Sugestão automática de vagas compatíveis com o perfil do candidato.
* Administração global: usuários, vagas, candidaturas, empresas (aprovação/rejeição) e estatísticas.
* Gestão de dados de localização (países, estados, cidades) e tabelas de referência do sistema.

=== Descrição dos Usuários

[cols="^,<,<", options="header"]
|====
| Perfil | Descrição | Acesso
| *CANDIDATO* | Busca vagas, se candidata e acompanha processos seletivos | Perfil próprio, vagas (leitura pública), candidaturas próprias
| *EMPRESA* | Publica e gerencia vagas; analisa candidaturas recebidas | Perfil próprio (sujeito a aprovação), vagas da empresa, candidaturas recebidas

== Requisitos

=== Identificação dos Requisitos
Os requisitos são identificados pelo prefixo `[RF]` (funcional) ou `[RNF]` (não funcional) seguido de número sequencial. A numeração é incremental e não reutilizada.

=== Prioridades dos Requisitos

* *Essencial*: o sistema não entra em funcionamento sem este requisito.
* *Importante*: o sistema funciona de forma incompleta sem este requisito; deve ser implementado.
* *Desejável*: não compromete o funcionamento básico; pode ser postergado.

== Requisitos Funcionais

=== [RF001] — Cadastro de Usuários

*Descrição*: O sistema deve permitir o cadastro público exclusivamente de candidatos e representantes de empresas. Contas administrativas não podem ser criadas pelo endpoint público.

*Atores*: Candidato, Empresa/Recrutador

*Prioridade*: Essencial

*Endpoint*: `POST /api/auth/register` (público)

*Entradas e pré-condições*:

[cols="<,<,<", options="header"]
|====
| Campo | Tipo | Regra de validação
| nome | String | Obrigatório, 3–100 caracteres
| email | String | Obrigatório, formato e-mail válido, único no sistema
| senha | String | Obrigatório, mínimo 6 caracteres
| dataNascimento | Date | Obrigatório, data no passado
| tipoUsuario | Enum | Obrigatório — exclusivamente CANDIDATO ou EMPRESA; ADMIN é rejeitado
|====

*Saída e pós-condição*: Conta criada. O campo `idade` é calculado automaticamente. O usuário fica ativo (`ativo = true`) e apto a realizar autenticação.

*Regras de negócio*:

* E-mail deve ser único; duplicata retorna erro 400.
* O tipo de usuário não pode ser alterado pelo próprio usuário após o cadastro.
* A criação ou promoção de ADMIN exige administrador autenticado, autorização explícita e registro de auditoria.
* Senhas são armazenadas com hash bcrypt (ver [RNF003]).

=== [RF002] — Autenticação

*Descrição*: O sistema deve permitir que usuários cadastrados realizem autenticação e recebam um token JWT para acesso às funcionalidades do seu perfil.

*Atores*: Candidato, Empresa, Administrador

*Prioridade*: Essencial

*Endpoints*:

* `POST /api/auth/login` (público) — autentica e retorna token JWT
* `POST /api/auth/logout` (autenticado) — encerra a sessão conforme a política de revogação definida em [RNF003]

*Entradas e pré-condições*: E-mail e senha válidos. Usuário previamente cadastrado com `ativo = true`.

*Saída e pós-condição*: Token JWT retornado. O token contém o `id`, `email`, `nome` e `tipoUsuario` do usuário e tem validade configurável (padrão 24 horas).

*Regras de negócio*:

* Usuários com `ativo = false` são rejeitados com erro 401.
* A autenticação usa JWT. Se não houver lista de revogação, o logout invalida apenas a credencial armazenada no cliente; esse comportamento deve ser informado e testado.
* O token deve ser enviado no cabeçalho `Authorization: Bearer <token>` em todas as requisições autenticadas.
* Endpoints públicos: `GET /api/vagas/**`, `GET /api/empresas/**`, `GET /api/localizacao/**`, `GET /api/lookup/**`.

---

=== [RF003] — Gerenciamento de Perfil do Candidato

*Descrição*: O sistema deve permitir que candidatos autenticados criem e atualizem seu perfil pessoal, incluindo dados profissionais, formações acadêmicas, experiências de trabalho e currículo.

*Atores*: Candidato

*Prioridade*: Essencial

*Endpoints* (requerem role `CANDIDATO`):

[cols="<,<,<", options="header"]
|====
| Método | Caminho | Descrição
| POST | `/api/candidatos` | Criar perfil de candidato
| GET | `/api/candidatos/meu-perfil` | Visualizar próprio perfil
| PUT | `/api/candidatos/meu-perfil` | Atualizar perfil (CPF, objetivo, pretensão, disponibilidade)
|====

*Entradas e pré-condições*:

[cols="<,<,<", options="header"]
|====
| Campo | Tipo | Regra
| cpf | String | Obrigatório, formato CPF brasileiro válido, único no sistema
| resumoProfissional | String | Opcional — objetivo profissional
| disponibilidade | String | Opcional — ex.: "imediata", "30 dias"
| pretensaoSalarial | BigDecimal | Opcional, valor ≥ 0,00
|====

*Saída e pós-condição*: Perfil do candidato criado ou atualizado. Dados disponíveis para filtragem de sugestões e visíveis em candidaturas conforme preferências de privacidade.

*Sub-recursos gerenciados pelo candidato*:

* *Formações* (`/api/candidatos/formacoes`): instituição, curso, nível, datas de início e fim.
* *Experiências* (`/api/candidatos/experiencias`): empresa, cargo, descrição, datas de início e fim.
* *Currículo* (`/api/candidatos/curriculo`): upload de arquivo (nome, caminho, tamanho, formato, data de upload).

*Regras de negócio*:

* Um usuário CANDIDATO só pode ter um perfil de candidato.
* CPF deve ser único no sistema; duplicata retorna erro 400.

=== [RF004] — Gerenciamento de Perfil da Empresa

*Descrição*: O sistema deve permitir que representantes de empresas ou recrutadores autenticados criem e atualizem o perfil da empresa. Após o cadastro realizado pelo usuário EMPRESA, o perfil fica com status *PENDENTE* e só se torna visível publicamente após aprovação do administrador.

*Atores*: Empresa/Recrutador, Administrador

*Prioridade*: Essencial

*Endpoints*:

[cols="<,<,<,<", options="header"]
|====
| Método | Caminho | Descrição | Acesso
| GET | `/api/empresas` | Listar empresas aprovadas | Público
| GET | `/api/empresas/{id}` | Buscar empresa aprovada por ID | Público
| GET | `/api/empresas/minha-empresa` | Ver próprio perfil (qualquer status) | EMPRESA
| POST | `/api/empresas` | Cadastrar empresa | EMPRESA ou ADMIN
| PUT | `/api/empresas/{id}` | Atualizar empresa | EMPRESA (própria) ou ADMIN
|====

*Entradas e pré-condições*:

[cols="<,<,<", options="header"]
|====
| Campo | Tipo | Regra
| cnpj | String | Obrigatório, formato CNPJ brasileiro válido, único
| razaoSocial | String | Obrigatório, máx. 150 caracteres
| nomeFantasia | String | Obrigatório, máx. 150 caracteres
| descricao | String | Opcional, máx. 500 caracteres
| porteId | Long | Obrigatório — referência à tabela `portes`
| ramoId | Long | Obrigatório — referência à tabela `ramos_atuacao`
| site | String | Opcional, URL válida (http/https)
| usuarioGestorId | Long | Opcional — apenas ADMIN pode informar para vincular a outro usuário
|====

*Fluxo de status*:

[cols="^,<,<", options="header"]
|====
| Status | Descrição | Visível publicamente?
| PENDENTE | Cadastro realizado, aguardando análise do administrador | Não
| APROVADA | Administrador aprovou o cadastro | Sim
| REJEITADA | Administrador rejeitou o cadastro | Não
|====

*Saída e pós-condição*: Perfil criado com status *PENDENTE* (se criado por EMPRESA) ou *APROVADA* (se criado por ADMIN). Após aprovação, a empresa aparece nas listagens públicas e fica apta a cadastrar vagas.

*Regras de negócio*:

* Um usuário EMPRESA só pode gerenciar uma única empresa.
* CNPJ deve ser único; duplicata retorna erro 400.
* O endpoint `GET /api/empresas` retorna apenas empresas com status *APROVADA*.
* O endpoint `GET /api/empresas/minha-empresa` retorna o perfil independentemente do status.
* A empresa pode editar seu perfil enquanto está *PENDENTE* ou *REJEITADA*; o status não é alterado pela edição.
* O ADMIN que cadastra uma empresa diretamente cria com status *APROVADA*.

=== [RF005] — Cadastro de Vagas

*Descrição*: O sistema deve permitir que empresas autenticadas e aprovadas cadastrem vagas de trabalho ou estágio. O servidor controla o estado inicial e a elegibilidade para publicação.

*Atores*: Empresa/Recrutador, Administrador

*Prioridade*: Essencial

*Endpoint*: `POST /api/vagas` (requer role `EMPRESA` ou `ADMIN`)

*Entradas e pré-condições*:

[cols="<,<,<", options="header"]
|====
| Campo | Tipo | Regra
| empresaId | Long | Obrigatório — empresa vinculada à vaga
| titulo | String | Obrigatório, 5–255 caracteres
| descricao | String | Obrigatório, mínimo 20 caracteres
| requisitos | String | Obrigatório
| tipoVagaId | Long | Obrigatório — referência a `tipos_vaga` (ex.: CLT, PJ, Estágio)
| modalidadeId | Long | Obrigatório — referência a `modalidades` (ex.: Presencial, Remoto, Híbrido)
| salarioMinimo | BigDecimal | Obrigatório, valor ≥ 0
| salarioMaximo | BigDecimal | Obrigatório, valor ≥ 0
| beneficios | String | Opcional
| cargaHoraria | String | Obrigatório — ex.: "40h/semana"
| escolaridadeId | Long | Obrigatório — referência a `niveis_escolaridade`
| areaAtuacao | String | Obrigatório, máx. 100 caracteres
| dataExpiracao | LocalDateTime | Obrigatório, data presente ou futura
| statusVagaId | Long | Não informado pelo cliente no cadastro; o servidor define o estado inicial
| numeroVagas | Integer | Obrigatório, mínimo 1
| cidadeId | Long | Obrigatório — referência a `cidades`
|====

*Saída e pós-condição*: Vaga registrada com data de publicação automática (`dataPublicacao = agora`) e estado inicial definido pelo servidor. A vaga só se torna elegível para busca e candidatura quando estiver ATIVA, não expirada e vinculada a empresa APROVADA.

*Regras de negócio*:

* Apenas a empresa proprietária e APROVADA ou um ADMIN podem cadastrar vagas em nome de uma empresa.
* O cliente não pode escolher diretamente o estado inicial da vaga.
* Campos de idade mínima/máxima ficam suspensos como critério de seleção até validação jurídica documentada.
* `salarioMinimo` deve ser ≤ `salarioMaximo`.

---

=== [RF006] — Manutenção de Vagas

*Descrição*: O sistema deve permitir que empresas autenticadas editem, pausem ou encerrem vagas próprias. Vagas com candidaturas não são excluídas fisicamente. O administrador pode alterar o estado de qualquer vaga mediante auditoria.

*Atores*: Empresa/Recrutador, Administrador

*Prioridade*: Essencial

*Endpoints*:

[cols="<,<,<,<", options="header"]
|====
| Método | Caminho | Descrição | Acesso
| GET | `/api/vagas` | Listar/filtrar vagas | Público
| GET | `/api/vagas/{id}` | Buscar vaga por ID | Público
| GET | `/api/vagas/empresa/{empresaId}` | Listar vagas de uma empresa | Público
| GET | `/api/vagas/minhas` | Listar vagas da empresa autenticada | EMPRESA
| PUT | `/api/vagas/{id}` | Atualizar dados da vaga | EMPRESA (própria) ou ADMIN
| DELETE | `/api/vagas/{id}` | Encerrar logicamente a vaga; exclusão física é vedada quando houver candidaturas | EMPRESA (própria) ou ADMIN
| PATCH | `/api/admin/vagas/{id}/status/{statusId}` | Alterar status de qualquer vaga | ADMIN
|====

*Entradas e pré-condições*: Dados atualizados da vaga ou identificador para remoção. Empresa autenticada e proprietária da vaga (ou ADMIN).

*Saída e pós-condição*: Vaga atualizada, pausada ou encerrada. Alterações são refletidas nas buscas; histórico e candidaturas permanecem íntegros.

*Regras de negócio*:

* Usuário EMPRESA só pode editar ou excluir vagas da própria empresa.
* O ADMIN pode alterar o status de qualquer vaga via endpoint dedicado.
* Toda alteração de estado registra estado anterior, novo estado, ator, data e motivo.
* Exclusão física somente é permitida quando não existirem candidaturas nem obrigação de retenção.

---

=== [RF007] — Busca e Filtragem de Vagas

*Descrição*: O sistema deve permitir a busca e filtragem de vagas ativas por múltiplos critérios. O acesso é público, sem necessidade de autenticação.

*Atores*: Candidato, qualquer visitante

*Prioridade*: Essencial

*Endpoint*: `GET /api/vagas` (público)

*Parâmetros de filtro disponíveis* (todos opcionais):

[cols="<,<", options="header"]
|====
| Parâmetro | Descrição
| titulo | Filtra por texto no título da vaga
| areaAtuacao | Filtra por área de atuação
| tipoVagaId | Filtra por tipo de vaga (CLT, PJ, Estágio...)
| modalidadeId | Filtra por modalidade (Presencial, Remoto, Híbrido...)
|====

*Saída e pós-condição*: Lista de vagas correspondentes aos critérios informados. Sem filtros, retorna todas as vagas disponíveis.

*Regras de negócio*:

* Os filtros são combinados (AND lógico).
* Por padrão, o backend retorna somente vagas ATIVAS, não expiradas e vinculadas a empresa APROVADA.
* Outros estados exigem endpoint autenticado e autorização compatível com o ator.
* Paginação, ordenação e valores padrão devem constar no contrato da API.

=== [RF008] — Candidatura à Vaga

*Descrição*: O candidato autenticado pode se candidatar a vagas de interesse. No momento da candidatura, pode configurar quais informações do seu perfil serão compartilhadas com o recrutador, atendendo aos princípios da LGPD.

*Atores*: Candidato

*Prioridade*: Essencial

*Endpoint*: `POST /api/candidaturas` (requer role `CANDIDATO`)

*Entradas e pré-condições*:

[cols="<,<,<", options="header"]
|====
| Campo | Tipo | Regra
| vagaId | Long | Obrigatório — identificador da vaga
| compartilharObjetivoProfissional | Boolean | Opcional, padrão `true`
| compartilharDisponibilidade | Boolean | Opcional, padrão `true`
| compartilharPretensaoSalarial | Boolean | Opcional, padrão `true`
| compartilharCurriculo | Boolean | Opcional, padrão `true`
| compartilharExperiencias | Boolean | Opcional, padrão `true`
| compartilharFormacoes | Boolean | Opcional, padrão `true`
| compartilharTelefone | Boolean | Opcional, padrão `false`
| compartilharEndereco | Boolean | Opcional, padrão `false`
|====

*Saída e pós-condição*: Candidatura registrada com data automática (`dataCandidatura = agora`) e as preferências de privacidade informadas. Confirmação retornada com HTTP 201.

*Regras de negócio*:

* A candidatura só é aceita para vaga ATIVA, não expirada e vinculada a empresa APROVADA.
* O candidato não pode se candidatar duas vezes à mesma vaga (constraint única `candidato_id + vaga_id`).
* Tentativa de candidatura duplicada retorna erro 400.
* O candidato pode atualizar suas preferências de privacidade a qualquer momento após a candidatura via `PATCH /api/candidaturas/{id}/compartilhamento`.

---

=== [RF009] — Acompanhamento de Candidaturas

*Descrição*: O sistema deve permitir que candidatos acompanhem o status das suas candidaturas e que empresas visualizem os candidatos inscritos nas suas vagas, com os dados exibidos conforme as preferências de privacidade de cada candidato.

*Atores*: Candidato, Empresa/Recrutador

*Prioridade*: Essencial

*Endpoints — Visão do Candidato* (requerem role `CANDIDATO`):

[cols="<,<", options="header"]
|====
| Endpoint | Descrição
| `GET /api/candidaturas/minhas` | Lista todas as candidaturas do candidato autenticado com seus respectivos status
| `GET /api/candidaturas/{id}` | Detalha uma candidatura específica
| `PATCH /api/candidaturas/{id}/compartilhamento` | Atualiza as 8 preferências de privacidade da candidatura
|====

*Endpoints — Visão da Empresa* (requerem role `EMPRESA`):

[cols="<,<", options="header"]
|====
| Endpoint | Descrição
| `GET /api/candidaturas/empresa` | Lista todas as candidaturas recebidas pela empresa autenticada
| `GET /api/candidaturas/empresa/vaga/{vagaId}` | Lista candidatos de uma vaga específica da empresa
| `GET /api/candidaturas/{id}/empresa` | Detalha uma candidatura na visão da empresa
| `PATCH /api/candidaturas/{id}/status/{statusId}` | Altera o estado por transição permitida e registra auditoria
|====

*Saída e pós-condição*: Candidato visualiza suas candidaturas com status atualizados. A empresa visualiza os candidatos com apenas os dados que cada candidato autorizou compartilhar; campos não autorizados são omitidos da resposta.

*Regras de negócio*:

* A empresa só visualiza candidaturas das suas próprias vagas.
* O candidato só visualiza as próprias candidaturas.
* Campos com `compartilhar* = false` são omitidos da resposta da visão da empresa quando a serialização usa `@JsonInclude(NON_NULL)`.
* A empresa proprietária pode alterar o estado de suas candidaturas somente por transições permitidas.
* Toda transição registra estado anterior, novo estado, ator, data e motivo.
* O ADMIN pode alterar o status de qualquer candidatura via `PATCH /api/admin/candidaturas/{id}/status/{statusId}`.

---

=== [RF010] — Administração do Sistema

*Descrição*: O sistema deve fornecer um conjunto completo de funcionalidades administrativas para gestão global de usuários, candidatos, empresas, vagas, candidaturas e administradores, incluindo o fluxo de aprovação de empresas e acesso a estatísticas do sistema.

*Atores*: Administrador

*Prioridade*: Essencial

*Pré-condição*: Usuário autenticado com `tipoUsuario = ADMIN`. Todos os endpoints abaixo têm prefixo `/api/admin`.

==== Estatísticas do Sistema

`GET /api/admin/estatisticas` — retorna contadores globais:

* `totalUsuarios`, `usuariosAtivos`, `usuariosInativos`
* `totalCandidatos`, `totalEmpresas`, `totalVagas`, `totalCandidaturas`, `totalAdmins`

*Saída e pós-condição*: Ação administrativa concluída com resultado explícito. Toda mutação registra operação, recurso, identificador, ator, data, resultado e motivo quando aplicável.

*Regras de negócio*:

* Nenhum endpoint público pode criar ou promover ADMIN; a promoção ocorre exclusivamente em `POST /api/admin/admins`.
* O sistema deve impedir que um administrador remova o próprio último privilégio quando isso deixar o sistema sem ADMIN ativo.
* Exclusões obedecem integridade referencial, política de retenção e direitos do titular; quando necessário, aplicam desativação, anonimização ou encerramento lógico.
* Alterações de tipo, aprovação de empresa, estados de vaga/candidatura e privilégios administrativos exigem auditoria.
* Estatísticas devem ser agregadas, autorizadas e não expor dados pessoais desnecessários.

=== [RF011] — Controle de Privacidade nas Candidaturas

*Descrição*: O sistema deve permitir que o candidato controle, de forma granular, quais informações do seu perfil são compartilhadas com o recrutador ao se candidatar a uma vaga, em conformidade com os princípios de minimização de dados da LGPD.

*Atores*: Candidato

*Prioridade*: Essencial

*Endpoints*:

* `POST /api/candidaturas` — campos de compartilhamento configurados no momento da candidatura (ver [RF008]).
* `PATCH /api/candidaturas/{id}/compartilhamento` — atualização das preferências a qualquer momento.

*Campos de privacidade controlados*:

[cols="<,<,<", options="header"]
|====
| Campo | Padrão | Dado protegido
| compartilharObjetivoProfissional | `true` | Objetivo profissional do candidato
| compartilharDisponibilidade | `true` | Disponibilidade de início
| compartilharPretensaoSalarial | `true` | Pretensão salarial
| compartilharCurriculo | `true` | Arquivo de currículo
| compartilharExperiencias | `true` | Histórico de experiências profissionais
| compartilharFormacoes | `true` | Formação acadêmica
| compartilharTelefone | `false` | Número(s) de telefone
| compartilharEndereco | `false` | Endereço residencial
|====

*Saída e pós-condição*: A visão da empresa em `GET /api/candidaturas/{id}/empresa` omite todos os campos cujo compartilhamento foi desativado pelo candidato. A preferência aplicada fica vinculada à finalidade, à data e à versão da política aceita.

*Regras de negócio*:

* O candidato pode alterar as preferências de qualquer candidatura a qualquer momento, sem efeito retroativo sobre acessos já legitimamente realizados.
* Campos de dados sensíveis (telefone, endereço) têm padrão `false` para proteção inicial por padrão.
* A empresa não tem acesso à configuração de privacidade — recebe apenas os dados autorizados.

=== [RF012] — Sugestão de Vagas para Candidatos

*Descrição*: O sistema deve oferecer ao candidato uma lista de vagas sugeridas automaticamente, calculada com base na compatibilidade entre o perfil do candidato e as características das vagas disponíveis.

*Atores*: Candidato

*Prioridade*: Importante

*Endpoint*: `GET /api/candidatos/sugestoes` (requer role `CANDIDATO`)

*Critérios de compatibilidade utilizados*:

* *Objetivo profissional*: vagas cuja `areaAtuacao` contém termos do objetivo profissional do candidato.
* *Pretensão salarial*: vagas com `salarioMinimo ≤ pretensaoSalarial ≤ salarioMaximo`.
* *Palavras-chave*: similaridade entre título/requisitos da vaga e objetivo, formação e experiências do candidato.
* *Faixa etária*: não participa do score enquanto não houver validação jurídica documentada.

*Saída e pós-condição*: Lista de até 10 vagas elegíveis, com score de 0 a 100, ordenadas por compatibilidade e excluindo vagas para as quais o candidato já se candidatou. Critérios, pesos, limiar e desempate devem ser versionados e compatíveis com a implementação.

*Regras de negócio*:

* Se nenhum critério de perfil estiver preenchido, o sistema retorna as vagas ativas mais recentes.
* Vagas já candidatadas são sempre excluídas da listagem de sugestões.
* O sistema deve fornecer explicação resumida dos principais fatores que contribuíram para cada recomendação.

=== [RF013] — Gestão de Dados de Localização

*Descrição*: O sistema deve manter uma base hierárquica de localização (países → estados → cidades) utilizada no cadastro de vagas e disponível publicamente para consulta.

*Atores*: Administrador (escrita), Qualquer usuário (leitura)

*Prioridade*: Importante

*Endpoints* (prefixo `/api/localizacao`):

[cols="<,<,<", options="header"]
|====
| Método | Caminho | Acesso
| GET | `/paises` | Público
| POST/PUT/DELETE | `/paises`, `/paises/{id}` | ADMIN
| GET | `/estados?paisId={id}` | Público (filtro por país opcional)
| POST/PUT/DELETE | `/estados`, `/estados/{id}` | ADMIN
| GET | `/cidades?estadoId={id}` | Público (filtro por estado opcional)
| POST/PUT/DELETE | `/cidades`, `/cidades/{id}` | ADMIN
|====

*Entradas e pré-condições*:

* *País*: nome (obrigatório), codigoIso (2 caracteres, obrigatório)
* *Estado*: nome (obrigatório, máx. 100 chars), uf (2 chars, obrigatório), paisId (FK obrigatório)
* *Cidade*: nome (obrigatório, máx. 100 chars), estadoId (FK obrigatório)

*Saída e pós-condição*: Dados de localização criados ou atualizados e disponíveis para uso no cadastro de vagas ([RF005]). Remoções preservam a integridade das referências existentes.

*Regras de negócio*:

* `codigoIso` é único por país; `uf` é única dentro do país e cidade é única dentro do estado conforme regra de normalização adotada.
* Não é permitido remover país com estados, estado com cidades ou cidade referenciada por vaga/endereço, salvo migração transacional previamente definida.
* Operações de escrita registram ator, data e resultado em auditoria administrativa.
* A API deve usar identificadores da hierarquia; cidade/estado em texto livre não substituem as referências canônicas.

=== [RF014] — Gestão de Tabelas de Referência do Sistema

*Descrição*: O sistema deve manter tabelas de referência (lookup) utilizadas nos formulários de vagas, candidatos e administração. A leitura é pública; a manutenção é restrita ao administrador.

*Atores*: Administrador (escrita), Qualquer usuário (leitura)

*Prioridade*: Importante

*Tabelas gerenciadas e seus endpoints* (prefixo `/api/lookup`):

[cols="<,<,<", options="header"]
|====
| Tabela | Endpoint | Uso
| Tipos de Vaga | `/vagas/tipos` | Tipo contratual da vaga (CLT, PJ, Estágio...)
| Modalidades | `/vagas/modalidades` | Formato de trabalho (Presencial, Remoto, Híbrido...)
| Escolaridades | `/vagas/escolaridades` | Nível mínimo de escolaridade exigido
| Portes | `/vagas/portes` | Porte da empresa (MEI, Pequena, Média, Grande...)
| Ramos de Atuação | `/vagas/ramos` | Setor da empresa (Tecnologia, Saúde, Educação...)
| Status de Vaga | `/vagas/status` | Estados possíveis de uma vaga (Ativa, Pausada, Encerrada...)
| Status de Candidatura | `/sistema/status-candidatura` | Estados do processo seletivo
| Tipos de Telefone | `/sistema/tipos-telefone` | Categorias de telefone (Celular, Fixo, WhatsApp...)
| Departamentos | `/sistema/departamentos` | Departamentos administrativos
|====

Cada tabela suporta: `GET` (público), `POST`, `PUT/{id}` e `DELETE/{id}` (ADMIN).

*Saída e pós-condição*: Tabelas de referência atualizadas e imediatamente disponíveis para uso nos formulários do sistema, sem invalidar registros existentes.

*Regras de negócio*:

* Identificadores já referenciados não podem ser reutilizados para outro significado.
* Exclusão é bloqueada quando houver referência; desativação lógica é preferida quando o valor não deve mais ser selecionado.
* API, UML, DER e código devem adotar uma representação canônica por conceito; não é permitido manter simultaneamente enum e lookup divergentes.
* Mudanças em estados de vaga ou candidatura devem preservar compatibilidade com as transições documentadas.
* Operações administrativas registram ator, data, alteração e resultado.

=== [RF015] — Direitos do Titular de Dados

*Descrição*: O sistema deve disponibilizar fluxo verificável para exercício dos direitos do titular relacionados aos dados pessoais tratados pelo MatchVagas.

*Atores*: Candidato, Empresa/Recrutador, Administrador responsável

*Prioridade*: Essencial

*Entradas e pré-condições*: Solicitação autenticada ou identidade validada, indicação do direito exercido e canal de resposta.

*Saída e pós-condição*: Solicitação protocolada com data, responsável, estado, prazo e resposta. O sistema deve permitir confirmação de tratamento, acesso, correção, exportação, revogação e eliminação ou bloqueio quando aplicável, registrando exceções legais de retenção.

*Regras de negócio*:

* A identidade do solicitante deve ser validada antes da entrega ou alteração de dados.
* Decisões automatizadas e recomendações devem possuir informação compreensível sobre critérios relevantes.
* Incidentes e solicitações devem manter trilha de auditoria sem expor dados além do necessário.
* Prazos operacionais e responsáveis devem constar em procedimento aprovado pelo controlador.

== Requisitos Não Funcionais

=== [RNF001] — Disponibilidade
*Descrição*: O sistema deve alcançar disponibilidade mensal mínima de 99,5% no intervalo de 08h às 20h. A medição deve declarar fórmula, fonte de telemetria, fuso horário e janelas de manutenção excluídas.

*Prioridade*: Importante

---

=== [RNF002] — Tempo de Resposta
*Descrição*: Busca, filtragem e candidatura devem apresentar p95 inferior a 3 segundos sob perfil de carga, volume de dados e ambiente versionados no plano de teste.

*Prioridade*: Importante

---

=== [RNF003] — Segurança — Autenticação e Senhas
*Descrição*: Senhas devem usar hash seguro e HTTPS é obrigatório em produção. A política deve definir senha, limitação de tentativas, recuperação, duração e rotação de JWT, gestão de chaves e efeito verificável de logout ou revogação.

*Implementação atual*: Spring Security 6 + jjwt (HS256), bcrypt via `PasswordEncoder`.

*Prioridade*: Essencial

---

=== [RNF004] — Privacidade e Proteção de Dados (LGPD)
*Descrição*: O sistema deve manter inventário de dados, finalidade e base legal, minimização, qualidade, retenção, descarte, auditoria de consentimento quando aplicável, resposta a incidentes e atendimento aos direitos definidos em [RF015]. Telefone e endereço permanecem desativados por padrão no compartilhamento.

*Prioridade*: Essencial

---

=== [RNF005] — Acessibilidade
*Descrição*: A interface deve atender à WCAG 2.2 nível AA. Os critérios aplicáveis devem estar ligados a testes automáticos e manuais, incluindo teclado, foco, contraste, mensagens de erro e leitores de tela.

*Prioridade*: Importante

---

=== [RNF006] — Compatibilidade
*Descrição*: Cada release deve publicar matriz de compatibilidade e testar a versão estável atual e a anterior de Chrome, Firefox, Edge e Safari, em superfícies desktop e móveis suportadas.

*Prioridade*: Importante

---

=== [RNF007] — Integridade de Dados
*Descrição*: Cadastro, candidatura, aprovação e transições de estado devem executar em transações ACID. Chaves estrangeiras e constraints devem proteger referências; o banco deve impor unicidade para `candidato_id + vaga_id`. Migrações devem ser versionadas, reversíveis quando tecnicamente possível e validadas em ambiente equivalente ao de produção.

*Critérios de verificação*:

* teste concorrente demonstra que duas candidaturas para o mesmo par não são persistidas;
* falha intermediária em operação transacional não deixa dados parciais;
* exclusão referenciada retorna conflito ou aplica a política documentada de desativação/anonimização;
* migração é aplicada a partir de uma cópia representativa sem perda inesperada.

*Prioridade*: Essencial

---

=== [RNF008] — Manutenibilidade
*Descrição*: O código deve manter separação Controller → Service → Repository, validação centralizada, mapeamento explícito e contrato OpenAPI versionado. Toda mudança deve passar por build reproduzível, testes automatizados e análise estática no CI.

*Critérios de verificação*:

* pull request falha quando build, testes, lint ou geração da documentação falham;
* alteração incompatível do contrato da API é detectada e registrada;
* dependências e versões suportadas são declaradas em arquivos de build;
* decisão que muda a arquitetura é registrada em ADR ou seção equivalente.

*Prioridade*: Importante

---

=== [RNF009] — Usabilidade
*Descrição*: Os fluxos críticos de cadastro, busca, candidatura, publicação de vaga e análise de candidatos devem possuir instruções, validação próxima ao campo, preservação de dados após erro e confirmação inequívoca do resultado.

*Critérios de verificação*:

* cenários, participantes, dispositivos, taxa de conclusão e tempo-alvo são definidos no plano de teste de usabilidade;
* erros informam causa e ação corretiva sem expor detalhes internos;
* layout permanece funcional nos tamanhos de tela declarados como suportados;
* ações destrutivas exigem confirmação e apresentam consequência.

*Prioridade*: Importante

---

=== [RNF010] — Confiabilidade
*Descrição*: Regras críticas devem ser aplicadas no backend e, quando cabível, reforçadas pelo banco. Respostas de erro devem usar formato padronizado e identificador de correlação; usuários inativos não autenticam e operações repetidas não podem produzir duplicação indevida.

*Critérios de verificação*:

* testes cobrem duplicidade, usuário inativo, autorização por propriedade e transições inválidas;
* erros 4xx não persistem alterações parciais e não expõem segredo ou stack trace;
* logs permitem correlacionar a requisição sem registrar senha, token ou dado pessoal desnecessário;
* procedimento de backup e restauração possui periodicidade, responsável e teste de recuperação registrados.

*Prioridade*: Essencial

== Rastreabilidade e controle da baseline
